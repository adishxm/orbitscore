# OrbitScore – Architectural & Product Assumptions (`ASSUMPTIONS.md`)

This document records all design, architectural, and domain defaults chosen for the OrbitScore reference-driven build, in compliance with §0 rule 2 of `orbitscore_master_prompt_v2.md`.

---

## 1. Product Identity & Safety Policy

1. **Brand Name vs. Functionality**:
   - The brand name is strictly **OrbitScore**, but the application **never** outputs a numeric score, letter grade, percentage readiness, risk rating, ranking, or green/red traffic-light status for any spacecraft mission.
   - The word "score" is strictly prohibited throughout all UI copy, error messages, tooltips, exports, and metadata, except within the brand name itself and the mandatory disclaimer:
     > *"Despite the name, OrbitScore does not score or certify missions; it organizes evidence for qualified human review."*
   - A dedicated automated test lint will verify that the forbidden word list (`certified`, `compliant`, `approved`, `guaranteed`, `safe to launch`, `risk score`, `readiness score`, `score of`, `pass/fail`, `cleared`, `ready for launch`) never appears in `/src` or generated export packets.

2. **Honest Status System**:
   - OrbitScore does not masquerade as a production backend system.
   - A persistent, prominent top banner displays: `DEMO / MOCK • SYNTHETIC DATA • LOCAL ONLY (not saved)`.
   - Every individual screen, view, and export packet features unambiguous status badges.
   - No mock login or deceptive authentication screens will exist. Clicking "Sign In" displays an informative modal explaining the production authentication roadmap (OAuth2 / OIDC + RBAC for qualified team and regulator review).

## 2. Evidence Vocabulary & Review Governance

1. **Evidence States (Exclusively 5)**:
   - `confirmed`: Verified by a designated human reviewer against primary source documents with an explicit locator and timestamp.
   - `unconfirmed`: Entered into the register from preliminary documentation, meeting notes, or vendor estimates, but lacking primary verification.
   - `missing`: A required parameter key identified by the selected profile that contains zero entries in the evidence register.
   - `conflicting`: Multiple evidence items recorded for the same parameter key that disagree beyond declared engineering tolerance thresholds.
   - `out-of-scope`: Evidence provided for spacecraft subsystems, payloads, or regimes not applicable to this mission's declared profile.

2. **Software Findings vs. Human Review Separation**:
   - **Software Findings** are strictly deterministic outputs generated by pure check functions. They never state "fail" or "rejected"; their vocabulary is: `Documented`, `Needs attention: missing`, `Needs attention: conflicting`, `Needs attention: unconfirmed`, or `Not applicable (out of profile scope)`.
   - **Human Review Decisions** are independent objects authored by qualified engineers or reviewers. They reference findings but never overwrite them. Permitted decision values: `Accepted for packet`, `Needs more evidence`, `Disputed`, `Deferred to specialist`, `Noted – no action`.
   - Software findings, human reviews, and open issues occupy distinct UI zones and export sections.

3. **Export Gating Rule**:
   - The export packet generation button remains disabled with clear visual feedback until **every** software finding has at least one associated human review decision (or is explicitly marked `Deferred to specialist`).

## 3. Technology Stack & Architecture Defaults

1. **Frontend Architecture**:
   - **Framework**: React 18 + TypeScript in strict mode (`"strict": true`, `"noImplicitAny": true`).
   - **Build Tool**: Vite 5 for fast HMR and lightweight bundle production.
   - **Styling**: CSS Custom Properties (`:root` tokens for design system) combined with CSS Modules (`.module.css`) for component encapsulation. This avoids heavyweight runtime CSS-in-JS and matches the reference site's custom-property architecture.
   - **State Management**: **Zustand** with an optional `localStorage` persistence middleware. Zustand is chosen over raw Context+Reducer because it provides fine-grained selector reactivity (preventing unnecessary re-renders of dense evidence tables) and simple serialization for "Reset Demo" and "Clear Local Data" workflows.
   - **Routing**: `react-router-dom` v6 with declarative routes matching the specification.
   - **Motion & Interaction**: **Framer Motion (Motion)** for declarative scroll reveals, layout animations, and modal/drawer transitions. It provides built-in `useReducedMotion` support to satisfy WCAG 2.2 accessibility requirements out-of-the-box.
   - **Icons**: `lucide-react` for crisp, consistent, accessible iconography with distinct shapes for all 5 evidence states.

2. **Typography Substitutions (Open License)**:
   - The reference site uses the commercial proprietary typeface *Magnetik*.
   - **Display / Headings**: **Space Grotesk** (Google Font, SIL Open Font License) – captures the geometric, technical, high-precision aesthetic of satellite mission engineering.
   - **UI / Body / Tables**: **Inter** (Google Font, SIL Open Font License) – provides unmatched legibility, tabular numerals (`tnum`), and distinct glyph distinctions.
   - **Data / Locators / Code**: **JetBrains Mono** or **IBM Plex Mono** – for parameter keys, timestamps, git hashes, and document locators.

3. **Deterministic Check Engine**:
   - Implemented as pure TypeScript functions in `/src/profiles/demo-evidence-completeness.ts`.
   - Zero DOM or browser dependencies; accepts a frozen array of `EvidenceItem` and outputs a frozen array of `Finding`.
   - Includes a full suite of Vitest unit tests verifying every edge case (missing values, unit mismatches, cross-source numerical conflict, expired source dates, unconfirmed items, and out-of-scope payloads).

4. **Persistence & Mock Backend**:
   - Default persistence: In-memory store initialized with the fictional **Asteria-3** 3U CubeSat dataset.
   - Optional local persistence: Browser `localStorage` key `orbitscore_state_v1`, with a visible banner warning that data is stored locally and unencrypted.
   - A typed API client interface in `/src/api/` with a `LocalMockAdapter` actively fulfilling calls, and an `HttpAdapter` stub alongside `openapi.draft.yaml` documenting the future FastAPI backend contract.
